How we protect your data

Version {{ policy_version }}. Section 8(5) of the Act and rule 6.

At rest

Every column that holds personal data is encrypted with a per column cipher before it reaches the database file, so a copy of that file is unreadable without the key. Passphrases are not encrypted, they are put through a slow one way key derivation function with a per account salt, which means we cannot read them back even if we wanted to.

Finding a row without decrypting the table

A sign in has to find one account out of many. Rather than decrypt every row, we keep a keyed digest of the contact address beside the encrypted value and look the digest up. The key is held separately from the index, so the column cannot be attacked with a precomputed list of common addresses.

Access

Every page that can reach personal data is behind a sign in, and the internal reports are behind a second check on top of that. Each read and each change is written to an audit trail with the purpose it was made under. The trail holds a reference to the row, never a second copy of its contents, and nothing personal is written to the application log.

In transit

A deployment terminates TLS in front of the application and sends a strict transport security header. This fixture is served over plain HTTP on the loopback interface so that it can be scanned locally, which a scan will and should report.

In the browser

A content security policy allows scripts, styles and images from this address only. There is no inline script anywhere, framing is refused, the referrer is not sent, and geolocation, camera and microphone are switched off.

If something goes wrong

A breach is recorded the moment it is detected, with a deadline of seventy two hours written onto the record itself. Two intimations then have to happen: one to the Data Protection Board of India and one to every affected person. They are tracked separately, because a system with only one of them will quietly skip the other.
